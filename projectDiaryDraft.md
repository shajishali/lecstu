### Self-Diary Entries

**Project Title:** Smart Faculty Access and Student Assistant System (LECSTU)  
**Month:** October 2025 - June 2026  
**Index Number:** CS/2020/063

**Week 1**  
Reviewed the overall concept of a smart academic assistant for university students and staff. Identified the main university problems to address, such as fragmented access to timetable information, lecturer details, appointments, room availability, and campus navigation. Considered different possible project directions and selected the idea of one integrated platform. The main issue at this stage was controlling the project scope, and it was solved by focusing on the most useful academic support functions.

**Week 2**  
Conducted the initial literature review on university support systems, academic chatbots, appointment management systems, campus navigation tools, and AI-based student assistance. Compared the features and limitations of previous studies. Identified that many existing solutions cover only one function and do not provide an integrated deployable platform. This helped define the research gap more clearly.

**Week 3**  
Refined the project scope and finalized the project title as Smart Faculty Access and Student Assistant System (LECSTU). Drafted the background, research problem, objectives, scope, and expected contributions. The main challenge was keeping the objectives realistic while preserving innovation, and it was solved by separating core features from higher-risk AI components.

**Week 4**  
Prepared the project proposal document by combining the literature review findings, methodology, feasibility analysis, and project timeline. Selected Design Science Research as the overall methodology because the study focused on the design and evaluation of a working artifact. Organized the proposal content into clear sections and prepared for the proposal presentation.

**Week 5**  
Started requirement analysis for the platform. Identified the main user roles as student, lecturer, and administrator. Defined the key functional requirements, including authentication, timetable viewing, lecturer availability checking, hall availability checking, appointments, notifications, chatbot support, voice interaction, indoor navigation, and translation support. Reviewed how these functions should interact with one another.

**Week 6**  
Worked on high-level system planning and architecture design. Divided the solution into frontend, backend, database, and AI service components. Considered how the web platform should communicate with speech, chatbot, and translation services. The main issue was handling integration complexity, and it was solved by planning separate service layers rather than building everything in one block.

**Week 7**  
Prepared the use case diagram and mapped the major interactions of students, lecturers, and administrators with the system. Identified the main workflows, including login, timetable checking, appointment booking, hall availability viewing, chatbot interaction, and navigation assistance. Adjusted the use cases to better reflect real-world academic tasks.

**Week 8**  
Designed the system architecture diagram and deployment view. Clarified how the web application, APIs, database, and AI components would operate together. Reviewed the infrastructure needed for a production-oriented deployment. The problem at this stage was showing technical complexity in a simple way, and it was solved by using layered diagrams.

**Week 9**  
Prepared the ER diagram and identified the main entities needed for the system. These included users, roles, timetables, lecturers, appointments, halls, notifications, navigation-related data, and assistant-related records. Revised the relationships several times to support the actual workflow of the platform and avoid unnecessary duplication.

**Week 10**  
Created sequence and workflow diagrams for major modules such as appointments, chatbot interaction, and indoor navigation. Focused on clarifying the steps from user input to system response. Faced difficulty representing AI-assisted flows in a simple sequence, so the sequence diagrams were reduced to the most important interactions.

**Week 11**  
Started UI and UX design for the main pages of the platform. Planned the login flow, dashboard structure, timetable page, lecturer directory, hall availability view, appointment interface, chatbot area, navigation page, and voice/translation features. Reviewed how students should move between the most common tasks with minimum clicks.

**Week 12**  
Improved the prototype and finalized the main screen designs. Checked whether the layout supported responsive access from desktop and mobile devices. Revised the interface after identifying some navigation and information-density issues. Simplified a few screens so users could find the important features more quickly.

**Week 13**  
Set up the development structure for the application. Organized the project into backend services, data models, user management, and feature modules. Decided on the main technologies for implementation and planned how AI functionality would connect to the main platform. This stage helped convert the design into a practical build plan.

**Week 14**  
Started building the authentication and role-based access control structure. Implemented the basic login-related flow and protected access according to user roles. This was important because the platform provides different information and functions depending on the type of user. Solved some early routing and permission issues during initial setup.

**Week 15**  
Implemented the main dashboard and core user-facing pages. Began connecting the interfaces for timetable access, lecturer information, and hall availability. Focused on keeping the interface clean and consistent. Adjusted component layouts where page sections were becoming too crowded.

**Week 16**  
Worked on the appointment management functionality. Planned the process for viewing availability, making appointment requests, and handling updates. Connected the data structures needed for booking-related records. The main issue was ensuring the workflow remained simple for both students and lecturers, and it was improved through clearer form design and status handling.

**Week 17**  
Built the notification-related functions and connected them to important user actions. Considered how notifications should appear when appointments are created, updated, or confirmed. Also reviewed the integration between dashboard updates and notification data. Made small backend and interface adjustments to keep the alert flow understandable.

**Week 18**  
Started work on the chatbot component. Planned the academic intents and entities needed for student-focused questions. Organized the chatbot interaction flow so it could answer questions related to academic support tasks. The challenge was keeping the domain focused, so the intent design was limited to the most useful university questions.

**Week 19**  
Continued chatbot development and improved the NLU-related design. Reviewed sample questions and checked whether the chatbot structure aligned with the system’s main functions. Began testing how the assistant would connect with the live platform features. Adjusted some intents and responses to reduce ambiguity.

**Week 20**  
Started integrating voice input support for English interaction. Explored the speech recognition workflow and tested how voice input could be converted into useful system actions. Reviewed latency and recognition quality across different settings. This stage revealed that accuracy and speed trade-offs needed to be measured properly during evaluation.

**Week 21**  
Worked on the translation-related component and how it would support the user interface and assistant features. Tested the practical feasibility of Tamil and Sinhala support. Found that quality varied across directions, so the project plan was updated to present translation as a partial contribution rather than a fully reliable completed feature.

**Week 22**  
Started the indoor navigation component. Planned the route guidance workflow, map support, and QR-based positioning concept. Reviewed how users would move from a building-level map into route instructions. The main issue was aligning technical feasibility with usability, and it was addressed by simplifying the positioning interaction.

**Week 23**  
Integrated the navigation workflow with the broader platform and refined the map-related interface. Continued connecting the different system modules so the platform behaved as one application rather than isolated parts. Resolved a few integration issues between modules by standardizing data flow and interface behavior.

**Week 24**  
Completed the major system workflows and conducted internal end-to-end testing. Verified the flows for authentication, timetable access, lecturer lookup, hall availability, appointments, notifications, chatbot support, and navigation assistance. Identified several minor UI and logic issues and corrected them before formal evaluation.

Reviewed system stability and ensured that the main features were ready for demonstration. This stage also helped prioritize which modules should be emphasized in evaluation.

Checked user opinions on timetable access, appointments, and assistant-related features. Identified that core academic functions were rated more positively than voice and translation features.
